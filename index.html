🧠 Blocos de comandos SQL — revisão rápida

Use este quadro para lembrar o significado de cada sigla e a qual família pertencem os principais comandos.

🏗️ DDL — Data Definition LanguageLinguagem de Definição de Dados
CREATE — criaALTER — alteraDROP — remove
📝 DML — Data Manipulation LanguageLinguagem de Manipulação de Dados
INSERT — insereUPDATE — atualizaDELETE — exclui
🔎 DQL — Data Query LanguageLinguagem de Consulta de Dados
SELECT — consulta
🔐 DCL — Data Control LanguageLinguagem de Controle de Dados
GRANT — concedeREVOKE — remove
🔄 TCL — Transaction Control LanguageLinguagem de Controle de Transações
COMMIT — confirmaROLLBACK — desfazSAVEPOINT — cria ponto de retorno
📚 Quero revisar o que cada bloco faz

DDL cria, altera ou remove a estrutura do banco.
DML insere, atualiza ou exclui dados.
DQL é usado para consultar dados.
DCL controla permissões de acesso.
TCL controla transações, permitindo confirmar, desfazer ou criar pontos de retorno.

Atalho mental: Estrutura → DDL • Dados → DML • Consulta → DQL • Permissão → DCL • Transação → TCL.

💻 Ver exemplos dos comandos SQL por bloco

🏗️ DDL — estrutura do banco

CREATE DATABASE helpnow; CREATE TABLE cliente ( id_cliente INT AUTO_INCREMENT PRIMARY KEY, nome VARCHAR(100) NOT NULL ); ALTER TABLE cliente ADD COLUMN telefone VARCHAR(20); DROP TABLE cliente;

📝 DML — manipulação dos dados

INSERT INTO cliente (nome, telefone) VALUES ('Livraria Saber', '99999-4444'); UPDATE cliente SET telefone = '98888-4444' WHERE id_cliente = 1; DELETE FROM cliente WHERE id_cliente = 1;

🔎 DQL — consulta dos dados

SELECT * FROM chamado; SELECT * FROM chamado WHERE status = 'Aberto' ORDER BY data_abertura DESC; SELECT ch.descricao, cl.nome AS cliente FROM chamado ch INNER JOIN cliente cl ON ch.id_cliente = cl.id_cliente; SELECT id_tecnico, COUNT(*) AS total FROM chamado GROUP BY id_tecnico HAVING COUNT(*) > 2;

🔐 DCL — controle de acesso

GRANT SELECT ON helpnow.* TO 'usuario'@'localhost'; REVOKE SELECT ON helpnow.* FROM 'usuario'@'localhost';

🔄 TCL — controle de transações

START TRANSACTION; SAVEPOINT antes_da_alteracao; UPDATE chamado SET status = 'Finalizado' WHERE id_chamado = 1; COMMIT; -- Se precisar desfazer: ROLLBACK; -- Ou voltar a um ponto específico: ROLLBACK TO antes_da_alteracao;

💡 Use estes exemplos como consulta rápida. Nas missões, tente montar e testar seu próprio comando antes de conferir um modelo.

🟣 Missão 1 — Qual tipo de banco usar?

Indicador 1: diferencia tipos de banco de dados conforme demanda e aplicabilidade.

Banco relacionalTabelas, linhas, colunas e relações bem definidas. Muito comum quando os dados são estruturados e relacionados.
Banco não relacionalPode usar documentos, chave-valor, colunas ou grafos. A estrutura e a forma de representar relações variam conforme o modelo.

💡 Dica para preencher: não responda apenas “porque é melhor”. Relacione sua escolha à estrutura dos dados, aos relacionamentos e ao que a HelpNow precisa fazer.

💡 Preciso de uma dica

Observe se os dados têm estrutura definida, se existem relações importantes e se a empresa precisa combinar informações dessas relações.

👀 Conferir uma possível resposta

Uma escolha adequada é relacional, pois os dados possuem estrutura definida e existem relações claras entre clientes, técnicos, categorias e chamados. O importante é a escolha estar coerente com os requisitos e ser justificada.

💡 Dica para preencher: pense no que acontece quando os registros não possuem sempre os mesmos campos e precisam aceitar estruturas variadas.

💡 Preciso de mais uma dica

Compare uma tabela com colunas previamente definidas com um documento que pode possuir campos diferentes de outro documento.

👀 Conferir resposta

Sim. Um banco orientado a documentos pode ser considerado porque permite trabalhar com estruturas mais flexíveis. Isso não significa que toda plataforma desse tipo seja obrigada a utilizar NoSQL: a decisão depende dos requisitos.

🔵 Missão 2 — Qual SGBD utilizar?

Indicador 2: define o Sistema Gerenciador de Banco de Dados de acordo com a aplicação.

📨 Nova decisão da equipe

A HelpNow aprovou a criação de um banco relacional. Agora a equipe precisa definir qual software será responsável por criar, armazenar, consultar e administrar esse banco. Sua tarefa não é escolher pelo nome mais conhecido: você precisa relacionar a escolha às necessidades do projeto.

SGBD é o software que gerencia o banco de dados. Não confunda: MySQL = SGBD MySQL Workbench = ferramenta gráfica

💡 Dica para escolher: pense no tipo de banco definido na Missão 1 e nas tecnologias utilizadas durante a UC.

💡 Dica para justificar: cite pelo menos uma característica da aplicação e explique por que o SGBD escolhido consegue atendê-la. Evite respostas como “porque é bom” ou “porque o professor ensinou”.

💡 Como pensar?

Considere estrutura dos dados, relacionamentos, recursos, segurança, custo/licença, escala e conhecimento da equipe. Não existe um SGBD universalmente “melhor”.

👀 Conferir resposta

Para esta atividade, MySQL é uma escolha coerente: é relacional e oferece os recursos necessários para implementar a solução trabalhada na UC. Outras escolhas podem ser justificáveis se forem coerentes com os requisitos.

🟢 Missão 3 — Transforme o problema em um banco

Indicador 3: cria banco de dados conforme requisitos da aplicação.

3.1 — Identifique as entidades

Pergunte: quem solicita? quem atende? o que é registrado? como o problema é classificado?

💡 Dica para preencher: procure os principais “objetos” sobre os quais a empresa precisa guardar dados. Use as perguntas do enunciado como guia.

👀 Conferir resposta

Uma solução possível: CLIENTE, TECNICO, CHAMADO e CATEGORIA.

3.2 — Defina atributos e chaves

PK identifica unicamente o registro. Pense: “quem sou eu?”. FK liga uma tabela a outra. Pense: “com quem estou relacionado?”.

💡 Dica para preencher: use os dados da planilha como ponto de partida. Para cada entidade, liste suas características e marque qual campo identificará cada registro de forma única.

💡 Preciso de ajuda com PK

Pergunte: “como o sistema distinguirá um cliente de outro, um técnico de outro e um chamado de outro?”. Um identificador como id_cliente pode cumprir esse papel.

👀 Conferir resposta

Uma possível organização é:

CLIENTE(id_cliente PK, nome, cnpj, telefone) TECNICO(id_tecnico PK, nome, especialidade) CATEGORIA(id_categoria PK, nome) CHAMADO(id_chamado PK, descricao, data_abertura, data_fechamento, status)

Por quê? Cada entidade reúne informações sobre um único assunto, e a PK identifica cada registro de forma única. As FKs serão adicionadas depois, quando transformarmos os relacionamentos em modelo lógico.

3.3 — Cardinalidade

💡 Dica para preencher: analise cada relação nos dois sentidos. Ex.: “um cliente pode ter quantos chamados?” e “um chamado pertence a quantos clientes?”. Só depois escolha 1:1, 1:N ou N:M.

👀 Conferir resposta
CLIENTE 1 ─── N CHAMADO TECNICO 1 ─── N CHAMADO CATEGORIA 1 ─── N CHAMADO

3.4 — Normalização: por que não deixar tudo em uma tabela?

💡 Dica para preencher: imagine que o telefone da Padaria Central mudou. Em quantas linhas seria necessário corrigir? O que poderia acontecer se uma delas fosse esquecida?

📚 Revisão rápida

1FN: valores atômicos e estrutura sem grupos repetitivos.
2FN: atributos dependem da chave completa.
3FN: evita dependências inadequadas entre atributos não-chave.

Ideia central: organizar os dados para reduzir repetição e inconsistência.

👀 Conferir resposta

O principal problema é a repetição dos mesmos dados. Por exemplo, nome, CNPJ e telefone de um cliente podem aparecer em várias linhas. Se o telefone mudar e apenas algumas linhas forem atualizadas, o banco poderá ficar com informações diferentes para o mesmo cliente.

Por quê? Separar os dados em tabelas adequadas reduz redundância e ajuda a evitar inconsistências. É essa organização que a normalização busca melhorar.

CREATE DATABASE helpnow; USE helpnow; CREATE TABLE cliente ( id_cliente INT AUTO_INCREMENT PRIMARY KEY, nome VARCHAR(100) NOT NULL, cnpj VARCHAR(20) UNIQUE, telefone VARCHAR(20) ); CREATE TABLE tecnico ( id_tecnico INT AUTO_INCREMENT PRIMARY KEY, nome VARCHAR(100) NOT NULL, especialidade VARCHAR(100) ); CREATE TABLE categoria ( id_categoria INT AUTO_INCREMENT PRIMARY KEY, nome VARCHAR(50) NOT NULL ); CREATE TABLE chamado ( id_chamado INT AUTO_INCREMENT PRIMARY KEY, id_cliente INT NOT NULL, id_tecnico INT NOT NULL, id_categoria INT NOT NULL, descricao VARCHAR(255) NOT NULL, data_abertura DATE NOT NULL, data_fechamento DATE, status VARCHAR(30) NOT NULL, FOREIGN KEY (id_cliente) REFERENCES cliente(id_cliente), FOREIGN KEY (id_tecnico) REFERENCES tecnico(id_tecnico), FOREIGN KEY (id_categoria) REFERENCES categoria(id_categoria) );

🎫 Ticket #001 — A HelpNow criou um novo requisito

Solicitante: Gerência de Atendimento

Demanda: “Percebemos que alguns chamados precisam ser atendidos antes de outros. A partir de agora, queremos registrar a prioridade de cada chamado como Baixa, Média ou Alta.”

A tabela chamado já existe, mas ainda não possui uma coluna para essa informação. Você precisa adaptar a estrutura existente sem apagar a tabela.

💡 Dica para escolher: a tabela já existe. Você não quer alterar o valor de um chamado específico; quer modificar a estrutura da tabela.

💡 Dica para escrever: informe qual tabela será alterada, que uma nova coluna será adicionada, o nome prioridade e um tipo adequado para textos curtos.

💡 Preciso de mais uma dica
ALTER TABLE nome_da_tabela ADD COLUMN nome_da_coluna TIPO;
👀 Conferir resposta
ALTER TABLE chamado ADD COLUMN prioridade VARCHAR(20);

🎫 Ticket #002 — Um novo cliente chegou

Solicitante: Equipe Comercial

Demanda: “Fechamos contrato com a Livraria Saber. Precisamos cadastrá-la para que ela possa abrir chamados.”

Dados recebidosNome: Livraria Saber
CNPJ: 44.444.444/0001-44
Telefone: 99999-4444

O cliente ainda não existe no banco. Sua tarefa é inserir um novo registro na tabela cliente.

💡 Dica para preencher: use INSERT INTO. Informe as colunas que receberão dados e, na mesma ordem, os respectivos valores. O id_cliente não precisa ser informado se estiver como AUTO_INCREMENT.

💡 Preciso de mais uma dica
INSERT INTO tabela (coluna1, coluna2) VALUES (valor1, valor2);
👀 Conferir resposta
INSERT INTO cliente (nome, cnpj, telefone) VALUES ('Livraria Saber', '44.444.444/0001-44', '99999-4444');

🎫 Ticket #003 — O atendimento começou

Solicitante: Central de Suporte

Demanda: “O técnico iniciou o atendimento do chamado de ID 1. Ele não pode mais aparecer como Aberto. Atualize sua situação para Em atendimento.”

Aqui não queremos criar um novo chamado nem mudar a estrutura da tabela. Precisamos modificar um dado que já existe.

💡 Dica para preencher: use UPDATE para escolher a tabela, SET para informar o novo valor e WHERE para garantir que somente o chamado 1 seja alterado.

💡 Preciso de mais uma dica
UPDATE tabela SET coluna = novo_valor WHERE identificador = valor;
👀 Conferir resposta
UPDATE chamado SET status = 'Em atendimento' WHERE id_chamado = 1;

🚨 Atenção: UPDATE sem WHERE pode alterar todos os registros da tabela. Antes de executar, pergunte: “quais linhas este comando atingirá?”.

🎫 Ticket #004 — A gerência quer uma lista de pendências

Solicitante: Gerência de Atendimento

Demanda: “Antes da reunião, preciso visualizar somente os chamados que ainda estão Abertos. Não quero os finalizados nem os que já estão em atendimento.”

Você não deve alterar nenhum dado. A tarefa é apenas consultar e filtrar os registros.

💡 Dica para preencher: comece com SELECT e FROM. Depois use WHERE para retornar somente as linhas cujo status seja igual a 'Aberto'.

💡 Preciso de mais uma dica
SELECT * FROM tabela WHERE coluna = valor;
👀 Conferir resposta
SELECT * FROM chamado WHERE status = 'Aberto';

🎫 Ticket #005 — Um registro foi criado por engano

Solicitante: Central de Suporte

Demanda: “Identificamos que o chamado de ID 6 foi cadastrado por engano e precisa ser removido.”

Excluir dados exige cuidado. Antes de executar o DELETE, confirme se o registro que será atingido é realmente o correto.

💡 Dica para preencher: pense em um comando que permita visualizar exatamente o registro de ID 6 antes de removê-lo.

💡 Dica para escrever: use DELETE FROM e não esqueça o WHERE. Sem filtro, você pode remover todos os registros da tabela.

💡 Preciso de mais uma dica

Primeiro faça um SELECT usando o mesmo WHERE que pretende utilizar no DELETE. Se o resultado estiver correto, prossiga.

👀 Conferir resposta

Uma boa prática é conferir primeiro:

SELECT * FROM chamado WHERE id_chamado = 6;

Depois excluir:

DELETE FROM chamado WHERE id_chamado = 6;
✅ O que você acabou de praticar?

Você respondeu a mudanças reais de um sistema: alterou estrutura, cadastrou dados, atualizou um registro, consultou informações e removeu um registro com segurança. O mais importante é perceber que cada comando surgiu de uma demanda, e não de uma lista de comandos para decorar.

🔗 JOINs

Use JOIN para combinar dados relacionados. Ex.: mostrar problema + cliente + técnico + categoria em vez de apenas IDs.

SELECT ch.descricao, cl.nome AS cliente, t.nome AS tecnico, c.nome AS categoria FROM chamado ch INNER JOIN cliente cl ON ch.id_cliente = cl.id_cliente INNER JOIN tecnico t ON ch.id_tecnico = t.id_tecnico INNER JOIN categoria c ON ch.id_categoria = c.id_categoria;
🔎 Subqueries e relatórios

Revise consultas dentro de consultas, COUNT/SUM/AVG/MIN/MAX, GROUP BY e HAVING. Lembre: WHERE filtra registros; HAVING filtra grupos.

🔐 DCL

GRANT concede permissões e REVOKE remove. A ideia principal é conceder apenas o acesso necessário.

🔄 TCL

START TRANSACTION inicia; COMMIT confirma; ROLLBACK desfaz; SAVEPOINT cria um ponto intermediário. Revise também ACID.

🛡️ LGPD

Revise tratamento responsável dos dados, finalidade, necessidade, acesso, segurança, direitos dos titulares e boas práticas.
